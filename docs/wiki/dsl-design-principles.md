## はじめに：DSL 設計が問うもの

言語指向プログラミング（LOP）において、DSL の構文は単なる「書きやすさ」の道具ではない。それは **ドメインの約束事（契約）を可視化し、変更の波及範囲を制御する構造そのもの** である。

イシュー #8 の議論は、一見すると「host/in-jail 構文を入れるか否か」という局所的な決定に見える。しかしその本質は、より深い問いであった：

> **「変更軸の階層」と「実行コンテキストのラベル」のどちらを構文の最上位に置くべきか？**

この問いに対する答えは、DSL 設計における **5 つの汎用原則** として一般化できる。  
本リポジトリ（makejail）への落とし込みは各節末と [three-axes-isomorphism](three-axes-isomorphism) を参照。

---

## 原則 1：変更軸の階層を構文の優先順位とせよ

### 観察

すべてのドメインには、変更頻度と影響範囲の異なる複数の **変更軸** が存在する。本ケースでは：

| 軸 | 変更頻度 | 影響範囲 |
|----|----------|----------|
| **個体** (individual / instance) | 高（新規 jail 作成ごと） | 局所的 |
| **種族** (family) | 低（アプリ版アップデートごと） | 全同種 jail に波及 |
| **運用** (operation / ops) | 中（組織方針ごと） | フリート全体 |

### 原則

**構文の最上位構造は、最も影響範囲が広く・最も変更が稀な軸から順に配置せよ。**

つまり：

```
運用プロファイル (operation)  ← 最上位（言語の受理集合）
  └── 種族定義 (family)       ← 中間（1 フォーム / 1 モジュール）
        └── 個体スロット      ← 最下位（個体ファイルの主内容）
```

実行コンテキスト（host/in-jail）は、この三軸よりもさらに下位のラベルに過ぎない。これを最上位に置くと、ある種族に属する個体の値が host/in-jail 両セクションに分散し、**同一変更軸上の情報が複数箇所に点在（ρ > 1）** する。

### 一般化された教訓

**構文の深さ（ネスト構造）は、ドメインの変更安定性の逆数に比例させる。**

すなわち、**変わらないものほど外側に、変わるものほど内側に** 配置する。

### makejail では

- 運用 = agent 既定の受理（cmd 不可、host ネット量産不可）  
- 種族 = `(wiki-site)` + `family/dokuwiki.rkt`  
- 個体 = `(instance …)` / `(arg …)`  
- host/in-jail **表面セクションは設けない**（#9）

## 原則 2：「展開」は言語責務とし、ユーザー仕様は宣言的に保て

### 観察

`sed` のような汎用コマンドを DSL 内で許容すると、ユーザーは「どのように設定を書き換えるか」を **手続き的に** 記述する。これにより：

- 言語は置換の成否を静的に検査できない  
- dry-run 出力は「sed を実行する」としか表示されず、**最終状態が不明**  
- 個体値（hostname 等）が複数コピーされ、変更漏れの温床となる  

### 原則

**ユーザーが記述するのは「何を（What）」までとし、「どのように実現するか（How）」は言語の展開層が担う。**

展開（expansion）とは、例えば：

- 種族定義に従って pkg リストを補完すること  
- 個体スロット値を所定の設定ファイルテンプレートに埋め込むこと  
- 運用プロファイルに基づいて不要なコマンドを除外すること  

これらはすべて言語内部のマクロ／モジュールで行い、ユーザーが書く個体ファイルには **生のシェル断片を一切書かせない**。

### 一般化された教訓

**DSL の境界は「ユーザーが責任を持つ宣言」と「言語が保証する展開」の間に引く。**

汎用言語のエスケープハッチ（sed, sh, eval）は、静的保証を無効化する **「契約違反ゲート」** であることを認識せよ。

### makejail では

- hostname → `template-subst`（言語側）  
- sed / 常用 `(cmd)` → 禁止方向（P02 / 0.4）  
- 種族展開表 → `family/dokuwiki.rkt`

## 原則 3：コンテキストラベルは主軸ではなく属性として扱え

### 観察

`(host ...)` / `(in-jail ...)` は、各命令がどこで実行されるかという **実行コンテキスト** を示す有用な情報である。しかし、これを構文上の第一区分にしてしまうと：

- ある種族の定義（pkg 群）が in-jail に、その設定ファイルが host に、と **同一種族の情報が分散**  
- レビュアーは「この copy は host で動くのか、in-jail で動くのか」を常に意識しながら読み解く必要がある  
- 新たな実行コンテキスト（例: bhyve ゲスト）が増えたとき、構文全体を再構成せざるを得ない  

### 原則

**実行コンテキストは、各命令の属性（attribute）またはメタデータとして保持し、構文上の主軸とはしない。**

本ケースの最終判断では、「個体スロットはほぼ全て in-jail（およびその jail のための配置）で動作する」という **ドメイン常識を前提** とし、コンテキストラベル自体を **構文から削除** する決断に至った。必要な場合は、dry-run 表示や内部 AST にのみコンテキスト情報を持たせる。

### 一般化された教訓

**構文の主軸は「ドメイン上の概念（種族・個体・運用）」に置き、実装詳細（実行ホスト、スレッド、トランザクション）は属性に格下げせよ。**

構文が実装都合で汚染されると、ドメインの進化に構文が追随できなくなる。

### makejail では

- host/in-jail は **ルールではなく自明の前提**（[three-axes-isomorphism](three-axes-isomorphism) §C）  
- 利用者プログラムは常に「一つの jail 個体の計画」

## 原則 4：ドメイン概念は「1 エントリポイント ＋ 1 モジュール」に閉じ込めよ

### 観察

種族（例: DokuWiki）の定義には、多数の要素が含まれる：

- インストールすべき pkg 群  
- 禁止すべきコマンド（forbid）  
- デフォルトの待ち受け  
- 設定ファイルテンプレートの配置  
- 依存するサービス  

これらを個体ファイルに毎回列挙すると、種族の仕様変更時に **全個体ファイルの修正が必要（ρ = N）** になる。

### 原則

**一つのドメイン概念（種族）に対して、外部に公開するエントリポイントはただ 1 つのマクロとし、その実装（展開表・テンプレート・制約）はただ 1 つのモジュールに隔離する。**

```racket
;; ユーザー個体ファイル（変更頻度：高）— 概念スケッチ
#lang makejail
(instance #:name "wiki-03"
          #:hostname "wiki-03.internal"
          #:data-host "/zroot/wiki-03/data")
(wiki-site)   ; ← 種族の唯一の入口（実装は family/dokuwiki.rkt）
```

```racket
;; 種族実装モジュール（変更頻度：低）— family/dokuwiki.rkt
;; packages / forbid / template-subst / services の展開表
```

### 一般化された教訓

**ドメイン上の「種類（type/family）」は、利用者に対しては単一の抽象名で提示し、その実体は言語モジュール内に隠蔽せよ。**

これにより「種族の変更」は 1 モジュールの修正に収束し、個体ファイル群は不変に保たれる（高凝集・低結合）。

### makejail では

- 入口: `(wiki-site …)`  
- 実装: `family/dokuwiki.rkt`（0.4）

## 原則 5：実装リファクタリングは表現力より回帰コストを優先せよ

### 観察

議論では `#lang br`（Beautiful Racket）への全面リライトが検討された。br はマクロ記述が簡潔になるが：

- 新たな依存（beautiful-racket 一式）が CI / 実行環境に追加される  
- 既存の `syntax-parse` による契約・テスト群を全て移植し直す必要がある  
- 本質的なドメイン表現力（構造化・検査）は `syntax-parse` でも十分実現可能  

### 原則

**技術的興味や記述の簡潔さだけで実装基盤を変更してはならない。**

評価軸は：

1. 本質的なドメイン表現力が向上するか（Yes/No）  
2. 既存の検証資産（契約、テスト、dry-run 出力）を維持できるか  
3. 移行コストに対して得られる利益が上回るか  

本ケースでは、三軸と同型は現行実装で十分に実装可能であり、br への移行は「手段の刷新」に過ぎず「ドメイン問題の解決」には直結しないと判断された。

### 一般化された教訓

**DSL の実装言語／フレームワークの選択は、「そのドメインで何を表現したいか」が先に立ち、「どう書けるか」は後から決めよ。**

新しい技法はプロトタイプや教育に限定し、本番 DSL では検証済みの基盤＋段階的進化を優先せよ。

### makejail では

- 本番: `racket/base` + `syntax-parse`  
- 教材: [lang-br-toolbox](lang-br-toolbox) · [beautiful-racket-stacker](beautiful-racket-stacker) · [stack-calc](stack-calc)

## 総括：DSL 設計とは「境界のデザイン」である

以上の 5 原則は、一貫して次の問いに答えるものである：

> **「ユーザーに何を書かせ、何を言語に隠すか」**

| 原則 | ユーザーに書かせるもの | 言語が隠す／保証するもの |
|------|------------------------|---------------------------|
| 1. 変更軸の階層 | 個体値（変わりやすい内側） | 種族・運用（変わりにくい外側） |
| 2. 展開の局所性 | 宣言的な「何を」 | 手続き的な「どうやって」 |
| 3. コンテキストの属性化 | ドメイン概念 | 実行コンテキスト（実装詳細） |
| 4. 1 マクロ＋1 モジュール | 種族名（抽象） | 種族の中身（具体） |
| 5. 実装の経済性 | 安定した構文 | 実装技法の変更（隠蔽） |

LOP の真価は、「**言語がドメインの約束事を保護する**」ことにある。構文はその保護のための鎧であり、鎧がドメインの関節（変更軸）に沿って可動し、かつ不要な実装の継ぎ目を露出させないことが、持続可能な DSL 設計の本質である。

### 最後に

本イシューで最終的に `(host ...)` / `(in-jail ...)` を **導入しない** という結論に至ったことは、一見「構造化の否定」に見えるかもしれない。しかし実際は、**「どの軸を主にするか」を厳格に問い直した結果としての、より高次の構造化** であった。

**DSL 設計において「何を構造化しないか」を決めることは、「何を構造化するか」と同等に重要な設計判断である。**
